# Technical Review — sym-pgp-ony (Lockpost)

**Date:** 2026-08-15  
**Reviewer:** Hermes Agent  
**Scope:** architecture, security, correctness, Docker/ops, tests, code quality  
**Status:** findings only — no code changes applied

---

## High — Security

- `TokenLinkService` uses AES-256-CBC without authentication before MAC verification
  - Risk: CBC is more error-prone than needed; encrypt-then-MAC ordering here is actually safe because HMAC is computed over `iv+ciphertext` and verified before decryption, but the primitive choice is still brittle.
  - Recommended fix: switch to AES-256-GCM (`openssl_encrypt(..., 'aes-256-gcm', ...)`) and store/verify the authentication tag.

- Production config hardcodes a PGP key ID in `config/packages/gpg.yaml`
  - Risk: ties prod to a specific identity; if the key rotates, the app breaks.
  - Recommended fix: derive the default key from env/config, or read the fingerprint from the actual imported key at runtime.

- `../../../.env.production.example` and `../../../.env.example` document a `%no-protection` / blank passphrase path
  - Risk: easy to deploy a server signing key with no passphrase.
  - Recommended fix: require passphrase in prod and make setup fail if absent; store the passphrase in a secrets manager or mounted secret file, not env.

- Key files are gitignored, but permissions/ownership are only enforced in Docker entrypoint and init scripts
  - Risk: on non-Docker deploys, keys may be world-readable.
  - Recommended fix: add a boot-time permission check in `PgpSigningService` and/or CI check that keys are `0600` and dirs `0700`.

- `/message/submit` returns raw exception messages in JSON on 500
  - Risk: stack/internal details leak to clients.
  - Recommended fix: return a generic error in prod; log details server-side only.

- `../../../.env.test` is excluded from reading by Hermes security, but tests still reference fixture key paths under repo `../../../config/pgp`
  - Risk: if the repo is cloned broadly, tests assume committed fixtures; ensure tests never require real key material.

## Medium — Architecture / Correctness

- `PgpSigningService::initializeGnuPG()` imports the private key and calls `addsignkey()` every call, while `signMessage()` reinitializes again internally
  - Risk: unnecessary repeated GPG initialization is expensive and inconsistent.
  - Recommended fix: instantiate once in constructor, store `$gpg`, reuse in `signMessage()` and `verifySignature()`.

- `verifySignature()` does not use the server key config context meaningfully; it imports a user-supplied public key into the same `GNUPGHOME`
  - Risk: mixing recipient verification material with server keyring is messy and may pollute trust.
  - Recommended fix: verify using an isolated in-memory/mini keyring, or `gpg --no-default-keyring --keyring /dev/null` semantics; avoid using server `GNUPGHOME` for arbitrary user keys.

- `TokenLinkService::deriveKey()` uses `hash('sha256', secret, true)`
  - Risk: no key stretching; if `APP_SECRET` is low entropy, brute-force is easy.
  - Recommended fix: use HKDF or PBKDF2 with salt, or enforce high-entropy `APP_SECRET`.

- Tests for signature verification expect failure strings like `verify failed`
  - Risk: assertions are tightly coupled to GnuPG wording and platform behavior.
  - Recommended fix: assert on summary/validity semantics rather than exact message text.

- `../../../.env.test` may be missing `APP_MAIL_FROM` and `PGP_PRIVATE_KEY_PASSPHRASE`
  - Risk: tests may behave differently on local machines.
  - Recommended fix: pin all required test env vars in `../../../.env.test` or `phpunit.xml.dist`.

## Medium — Docker / Ops

- `../../../docker-compose.yml` maps `./config/pgp` as a Docker volume, but init scripts also create keys inside the container filesystem
  - Risk: host bind mount can override container-generated keys or vice versa.
  - Recommended fix: document whether keys are generated by script or mounted; if mounted, skip init script.

- `../../../docker-compose.prod.yml` uses `network_mode: host`
  - Risk: removes container network isolation; port conflicts; reduced portability.
  - Recommended fix: prefer bridge + explicit ports unless you need host networking for mail integration; if kept, add strong documentation.

- Dockerfile uses `php:8.3-fpm` while `../../../composer.json` says `>=8.2` and README says `PHP 8.3`
  - Recommendation: align docs and composer constraints; add explicit platform lock to avoid mismatches.

- MailHog container exists in dev compose, but no healthcheck / readiness gate
  - Risk: PHP tests may attempt SMTP before MailHog is ready.
  - Recommended fix: add `healthcheck` and make `depends_on` condition-based if needed.

## Low — Code Quality / Maintenance

- `ErrorHandler::handleControllerException()` builds raw HTML
  - Risk: XSS if `$customMessage` or exception text contains HTML; also bypasses templates.
  - Recommended fix: render a Twig error template with proper escaping.

- `DefaultController::submitMessage()` trusts the JSON field name `encrypted` but route doc and client naming may drift
  - Risk: mismatch between DTO property name and client payload.
  - Recommended fix: keep DTO and client-side field names documented; validate content structure before signing/sending.

- README says PHP 8.3-FPM but Dockerfile composer install path suggests 8.2-capable image; clarify exact tested version.

- `public_key_path` in `gpg.yaml` prod block uses `%kernel.project_dir%` despite absolute `/var/www/app` usage elsewhere
  - Risk: path inconsistency across configs.
  - Recommended fix: keep paths consistent and document override mechanism.

## Quick Wins

- Add a `docker-compose.override.yml` for local dev defaults so `../../../docker-compose.yml` is safe to deploy.
- Add a `Makefile` or `bin/dev` script for repeated Docker/test commands.
- Add rate limiting on `/message/submit` and `/submit/{token}` to reduce abuse.
- Add CSP nonce/hash audit if you want stronger browser crypto controls.
- Add a simple `bin/console app:pgp:check` command to validate key presence/permissions at deploy time.
